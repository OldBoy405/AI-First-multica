1设计理念与目标

Multica 的口号是 “Your next 10 hires won't be human”（你的下 10 位新员工不会是人类）。它是一个开源的托管智能体平台（managed agents platform）：把编码智能体变成真正的团队成员——你像给同事派活一样把 Issue 指派给智能体，它自主领取任务、写代码、汇报阻塞、发表评论、更新状态。

名字来源：Multiplexed Information and Computing Agent——致敬分时操作系统 Multics，寓意人类与智能体在同一团队中“分时复用”协作。

1.1 核心设计哲学

  • 智能体是一等公民（Agents as Teammates）：智能体拥有档案、出现在看板上、可被指派/评论/@提及，是多态的 assignee（assignee_type + assignee_id 可指向成员或智能体）。与人类不同：它会自主开工，且不接收任何收件箱通知。
  • 厂商中立（Vendor-neutral）：支持 14 种智能体 CLI——Claude Code、Codex、GitHub Copilot CLI、Gemini、Cursor Agent、OpenCode、Kimi 等。平台不绑定任何模型厂商。
  • 本地执行、隐私优先：智能体永远运行在用户自己的机器上（通过本地 daemon），服务器永远看不到你的 API Key、代码目录和授权工具链。云端和自托管都遵循这一原则。
  • 人机混合团队：Squads（小队）可以把智能体和人类编入同一小组，由一个 Leader 智能体负责路由分工（@FrontendTeam 而不是 @alice-or-bob）。
  • 可自托管的开源产品：Docker Compose 两条命令起全栈，或用 Helm chart 上 Kubernetes。

1.2 工程理念（从代码库归纳）

  • 防御性 API 边界：前端所有网络 JSON 必须经 zod schema + parseWithFallback 解析，永不 as T 硬转——因为已安装的桌面客户端可能连接更新版本的后端，响应漂移不能白屏。
  • 严格的状态二分法：TanStack Query 独占服务器状态，Zustand 独占客户端/视图状态，二者不得互相镜像。
  • 三层共享包 + 单向依赖：views → core + ui，core 与 ui 相互独立；平台差异全部收敛到适配器（NavigationAdapter / StorageAdapter / LocaleAdapter）。
  • 移动端刻意独立：只共享类型和纯函数，“复制设计而非复制导入”，UI 可以为手机场景自由发挥，但产品语义（计数、权限、枚举、数据身份）必须与 Web 完全一致。
  • 推送优先的实时性：React Query 默认 staleTime: Infinity，数据新鲜度靠 WebSocket 推送而非轮询。
  • 内部代码不留兼容层：非边界代码禁止兼容垫片/双写/遗留适配器；被替换的流程直接删除旧路径。

1.3 核心产品概念

概念说明
Workspace自包含的协作空间；每个 Issue、成员、评论、智能体都恰好属于一个工作区。所有查询按 workspace_id 过滤，X-Workspace-ID 请求头选择工作区。
Issue工作的核心单元，可指派给人或智能体；具有状态/优先级/截止日期/看板排序位置、子 Issue、所属项目、元数据键值对和订阅者。
Project聚合相关 Issue；Project Resources 可挂接类型化的资源指针（Git 仓库、本地目录）作为智能体的上下文范围。

Inbox / ChatInbox 是人类被打断的地方（指派、提及、订阅动态、失败任务）；Chat 是与智能体的私密 1:1 会话，完全沙箱化（智能体看不到 Issue），通过 provider 会话恢复保持多轮上下文。

2.2 Monorepo 与依赖方向

仓库使用 pnpm workspaces（apps/* + packages/*）+ Turborepo。共享包导出原始 .ts/.tsx（通过 package.json 的 exports 映射），由消费应用自行编译——因此 Turbo 的 typecheck 任务采用拓扑依赖（^typecheck），且 test/lint 都以 typecheck 为门槛。

硬性边界约束（CLAUDE.md 明文规定）
  • packages/core：禁止 react-dom、localStorage（用 StorageAdapter）、process.env、UI 库。

2.3 任务执行生命周期

智能体执行的核心链路：服务器只做编排，daemon 在用户本机领取任务、创建隔离工作目录、拉起对应的智能体 CLI、把结果流式回传。

U->>S: 指派 Issue 给智能体 (REST) S->>S: 创建 Task (queued) D->>S: 轮询 (每 3s) 领取任务 S-->>D: Task → dispatched D->>D: 创建隔离工作目录 D->>A: 拉起智能体进程 S-->>U: WebSocket 推送状态变更 A-->>D: 流式输出 / 评论 / 状态更新 D->>S: 回传进度与结果 (心跳 15s) S-->>U: WS 实时更新 (running → completed/failed)

2.4 状态管理架构

前端状态被严格切成两半，这是整个代码库最具纪律性的约定之一：

TanStack Query（服务器状态）Zustand（客户端状态）
管什么Issues、用户、工作区、收件箱、智能体、成员——一切来自 API 的数据筛选器、草稿、模态框、标签页布局、导航历史
缓存策略staleTime: Infinity，新鲜度靠 WebSocket 推送（patch 或 invalidate）persist 中间件 + 工作区命名空间存储（key:slug）
Key 约定工作区级 Query Key 必须包含 wsId；key 工厂区分“失效前缀”与“完整 key”共享 store 只能放 packages/core；selector 必须返回稳定引用
禁区WS 事件严禁把服务器数据镜像进 Zustand严禁持久化服务器数据或临时 UI 状态
乐观更新准则 只有同时满足四个条件才允许乐观更新：结果本地可预测、用户停留在同一屏（无导航）、失败罕见、回滚trivial。典型场景是状态/指派/开关字段的 patch。会导航或需确认的流程（创建、删除、退出）必须先等服务器响应；聊天发送采用“pending 消息”模式——立即渲染可见的等待态并支持失败重试，而不是静默乐观。

3各模块功能结构

3.1 server/ — Go 后端服务

Go 模块 github.com/multica-ai/multica/server，Go 1.26.1。没有 Web 框架（仅 Chi 路由）、没有 ORM（sqlc 生成类型安全查询）、没有迁移库（手写运行器）。

入口二进制（cmd/）

二进制职责
cmd/serverAPI 服务器：启动 slog、特性开关、pgx 连接池、事件总线、两个 WebSocket Hub、Redis 中继、指标注册表，然后构建路由。还承载后台工作者：运行时清扫器（标记失联 Runtime 离线）、Autopilot 失败监控、批量心跳调度器、DB 调度器、渠道 Supervisor。优雅关闭有明确顺序：HTTP 排空 → 清扫器 → 心跳刷写 → 渠道 Supervisor → 指标。
cmd/multica单一 cobra 二进制 = CLI + daemon。命令组：issue/project/agent/autopilot/workspace/skill/squad/chat + daemon/runtime + auth/login/setup/config/update。智能体自己也会调用这个 CLI（如 multica repo checkout）。
cmd/migrate迁移运行器 up|down（详见下文）。
cmd/backfill_*两个一次性运维回填工具。

路由与中间件（cmd/server/router.go，~1490 行）

全局中间件链：RequestID → ClientMetadata → RequestLogger → HTTP 指标 → Recoverer → CSP → CORS。路由分四大组：

  • 公开组：/health、/readyz、/ws、认证端点（每 IP Redis 限流）、Webhook（凭证在载荷里：GitHub HMAC-SHA256、Autopilot token、Stripe）。
  • Daemon 组：/api/daemon/*，专用 DaemonAuth——注册/心跳/WS/任务领取（claim、prepare-lease）/生命周期回调（start/progress/complete/fail/usage）。
  • 用户级保护组：/api/me、PAT 管理、邀请、计费（额外 RequireHumanActor——任务令牌被 403）。
  • 工作区作用域组：issues/labels/projects/squads/autopilots/agents/skills/chat/inbox 等全部业务端点，由 RequireWorkspaceMember 把守；URL 参数型工作区路由再分 member/admin/owner 三档角色。

认证令牌模型（前缀分派）

前缀类型说明
mat_智能体任务令牌服务器按任务铸造；绑定单一工作区、标记 X-Actor-Source: task_token，被账户级端点拒绝——智能体的 API 权限被严格限制在任务作用域内
mul_个人访问令牌（PAT）哈希查找 + Redis 缓存，异步更新 last_used_at；CLI 登录默认 90 天

中间件会先剥掉客户端自带的 X-Actor-Source 再走分支，然后由服务器重新盖章 X-User-ID/X-Workspace-ID——身份头永远不可伪造。工作区解析优先级：任务令牌绑定（不可覆盖）→ 中间件上下文 → X-Workspace-Slug 头 → 查询参数 → X-Workspace-ID 头。非成员一律返回 404（不泄漏存在性）。

数据库

  • pgx/v5 + pgxpool，无 ORM；另建一个小连接池专供指标采样器，防止卡住的抓取饿死请求流量。
  • sqlc：查询在 pkg/db/queries/（38 个 .sql 按领域划分），schema 即 migrations/，生成到 pkg/db/generated。
  • 迁移：198 对 up/down；跨副本并发安全靠会话级 advisory lock（固定在单个连接上）+ schema_migrations 版本表跳过已应用项；刻意不包成单事务（部分迁移用 CREATE INDEX CONCURRENTLY）；支持按版本号挂前置钩子。/readyz 校验磁盘上每个版本都已记录，而非只看最新。
  • 扩展：pgcrypto、pg_trgm、pg_bigm（Issue 全文/三元组搜索）。未使用 pgvector——虽然镜像是 pgvector/pg17，但没有任何向量列或嵌入。

  • 浏览器 Hub（internal/realtime）：连接即自动订阅 workspace:{id} 与 user:{id}，task/chat 等更细作用域通过 subscribe 帧按需订阅并经 ScopeAuthorizer 授权。个人事件（inbox、邀请）只走 SendToUser，永不进工作区广播。
  • 多节点扇出：设置 REDIS_URL 后由 REALTIME_RELAY_MODE 选择——默认 sharded（Redis Streams，8 分片、MAXLEN 10 万、5 分钟启动重放窗口，客户端用 ULID 去重）；保留 legacy pub/sub 与 dual 双写模式用于迁移。中继读/写/存储使用独立 Redis 客户端，阻塞式流读取不会饿死请求路径。
  • Daemon Hub（internal/daemonws）：唤醒是纯提示（低延迟），任务领取仍走 HTTP claim——WS 断连不影响正确性，只影响延迟。

智能体子系统

  • 多态指派：issue.assignee_type ∈ {member, agent, squad} + assignee_id。issue_trigger.go 决定写入是否触发运行（指派触发 / 从 backlog 提升状态触发），并通过 preview-trigger 端点让 UI 在写入前预演同一决策。
  • TaskService：拥有 agent_task_queue 表和全部入口（按 Issue/提及/线程/小队 Leader/快速创建/聊天 enqueue），每次入队还会计算该任务的 Composio MCP overlay；Redis EmptyClaimCache 短路“该 Runtime 无任务”的空轮询。
  • pkg/agent 统一后端：一个 Backend 接口——Execute(ctx, prompt, ExecOptions) (*Session, error)，Session 流式产出统一的 Message（text/thinking/tool-use/tool-result/status/error）。14 种后端全部是子进程包装器而非 API 客户端（如拉起 claude --output-format stream-json 解析 NDJSON）。ExecOptions 归一化跨厂商关注点（模型、系统提示、超时、会话恢复 ResumeSessionID、MCP 配置、思考等级），后端对不理解的字段选择忽略而非报错。
  • 内置技能：go:embed 嵌入 8 个 multica- 前缀技能（working-on-issues、creating-agents、squads 等），每个智能体在工作区技能之上自动获得。
  • 渠道引擎：Lark（WS 长连接）与 Slack（Socket Mode）注册到平台无关的 Registry/Supervisor/Router，共享与 HTTP 相同的 IssueService/TaskService——消息突发经防抖批处理折叠成一次智能体运行；各集成按环境变量门控，未配置时返回 503 而不阻塞启动。

[workspaceSlug]/认证后的应用壳。layout.tsx 是认证 + onboarding + 工作区解析的门卫；(dashboard) 组下有 issues、projects、my-issues、inbox、chat、agents/[id]、autopilots/[id]、skills/[id]、squads/[id]、runtimes/[id]、members/[id]、settings、usage、billing

关键设计：apps/web/platform/ 目录只有一个文件——navigation.tsx（Web 版 NavigationAdapter，包装 next/navigation，提供 prefetch）。几乎全部 UI 都住在 packages/views 里（web 自己的 components/ 只有 3 个文件）。工作区身份由路由驱动：[workspaceSlug]/layout.tsx 在渲染阶段调用 setCurrentWorkspace(slug, id)，保证第一个子查询就带上正确的 X-Workspace-Slug 请求头。

3.3 apps/desktop — Electron 桌面应用

技术栈：Electron 39 + electron-vite 5 + electron-builder 26 + electron-updater；渲染层为 React + react-router-dom 7（内存路由）+ Tailwind 4。

三进程结构（src/）

  • main/：创建 BrowserWindow（hiddenInset 标题栏）、注册 multica:// 协议、大量 IPC 模块——daemon-manager.ts（管理本地 daemon 生命周期）、cli-bootstrap.ts、updater.ts、快捷键/手势/右键菜单/外链安全打开等，大多带同目录测试。
  • preload/：contextBridge 暴露 desktopAPI（运行时配置、通知、未读角标、目录选择等）与 daemonAPI（start/stop/restart/syncToken/日志流）。
  • renderer/：React 应用，含独有的多标签页系统。

标签页系统（桌面独有）

stores/tab-store.ts 用 Zustand + persist 维护 byWorkspace: Record<slug, {tabs, activeTabId}>——每个 Tab 拥有自己独立的 react-router DataRouter（createMemoryRouter）和历史索引；固定（pinned）标签排最前、仅图标、不可关闭，任何改变路径的跳转会自动开新标签。tab-content.tsx 用 React 的 <Activity mode="visible"|"hidden"> 渲染所有标签，隐藏标签保留 DOM 与状态。

WindowOverlay：预工作区流程不是路由

创建工作区、接受邀请、onboarding 这类“一次性动作”在桌面端被建模为窗口级覆盖层状态（stores/window-overlay-store.ts），而不是路由——因为桌面 URL 不可见、标签系统会尝试持久化路由、邀请深链没有分发目标。这是 CLAUDE.md 中“Transition flows are WindowOverlay state, not routes”规则的实现。

导航适配器的三个拦截器

桌面版 NavigationAdapter 在委托给 react-router 之前依次尝试：tryRouteToOverlay（过渡路径 → 窗口覆盖层）、tryRouteToOtherWorkspace（前导 slug 不同 → 切换工作区）、tryRouteToPinnedNewTab（固定标签上的路径变更 → 开新标签）。push("/login") 被直接翻译成登出。

3.4 apps/mobile — Expo / React Native

技术栈（锁定基线）：Expo SDK 55、React Native 0.83.6、React 19.2.0（直接锁定、不走 catalog）、expo-router 55、NativeWind 4 + Tailwind 3.4（与 web/desktop 的 Tailwind 4 刻意不同——NativeWind 5 尚不稳定）、react-native-reusables 组件约定、TanStack Query 5（移动端自有 QueryClient）、expo-secure-store 存 token。

移动端独立性原则 Mobile 只允许从 @multica/core 导入类型（import type）和纯函数（实测：types ×90、日期工具 ×6 等），完全不引用 @multica/ui / @multica/views。UI 与交互可以为手机自由发挥，但四件事必须与 web/desktop 完全一致：计数与可见性、权限、状态枚举与流转、数据身份。有记录的事故：mobile 直接渲染原始 GET /api/inbox 行，显示 3 个未读点而 web 显示 1 个——修复是把 deduplicateInboxItems 的逻辑镜像到 apps/mobile/lib/inbox-display.ts。教训被固化为规则：渲染列表前必须先查 core 里有没有 dedupe/coalesce 预处理。

路由（expo-router 文件路由）：(auth)/login+verify → (app)/[workspace]/(tabs)/（inbox、my-issues、chat、more）→ Issue/Project 详情栈 + 各种 formSheet 选择器。实时策略分三层：无 React 的 ws-client.ts（指数退避 + 全抖动）→ realtime-provider.tsx（随认证/工作区/AppState/NetInfo 重挂载）→ 每特性的订阅 hook；蜂窝数据规则是 patch 优先于 invalidate。移动端自己维护 data/realtime/*-ws-updaters.ts，明令禁止导入 core 的版本（“copy the design, not the import”）。

3.5 apps/docs — 文档站

Next.js 15 + Fumadocs 15，basePath: /docs，由 web 应用的 rewrite 代理（/docs/* → DOCS_URL，默认 4000 端口）。四语言（en 默认无前缀 / zh / ko / ja），文件名点后缀模式（page.zh.mdx），共 136 个 MDX 文件。内容分区：入门（how-multica-works、cloud-quickstart、self-host-quickstart）、Workspace & team、Agents、How agents run、Collaborating with agents、Inbox、Integrations、Self-hosting & ops、Reference（CLI/令牌/桌面/移动）、Developers（conventions 命名与 i18n 词汇表——CLAUDE.md 指定的唯一权威来源）。文档站与应用运行时完全解耦：只依赖 @multica/ui 的 4 个导入。

3.6 packages/ — 共享包结构

packages/core — 无头业务逻辑层

按领域组织（不是按技术层）：issues/、inbox/、agents/、chat/、runtimes/、projects/、autopilots/、billing/ 等 20+ 领域文件夹，每个领域内重复同一套文件词汇：queries.ts（key 工厂 + queryOptions）、mutations.ts、ws-updaters.ts（把 WS 增量直接打进 Query 缓存）、stores/。package.json 有约 110 个 exports 子路径入口，根 barrel 刻意极小。

  • ApiClient 单例：模块级 Proxy 单例（boot 时 setApiInstance()），~89KB 的单类；预初始化访问返回 undefined 以兼容 HMR。
  • parseWithFallback（api/schema.ts）：safeParse 成功返回数据，失败记录 warn 并返回 fallback，永不抛出——契约漂移让页面降级而不是白屏。schema 约定：枚举保持 z.string()（未知值仍可解析）、可选字段 union null、数组 .default([])、每个对象以 .loose() 结尾。
  • 工作区感知存储：createWorkspaceAwareStorage 把持久化 key 命名空间化为 key:slug；无活跃工作区时读返回 null、写直接丢弃（曾经的裸 key 回退导致状态跨工作区泄漏）。
  • paths/：零依赖 URL 构建器，共享代码导航的强制入口（paths.workspace(slug).issueDetail(id)，22 个构建器），保留 slug 列表由脚本生成。
  • i18n 三入口拆分：i18n（服务器安全，零 React/DOM）、i18n/react（react-i18next 会在模块加载时 createContext，在 RSC 下会崩）、i18n/browser（碰 document.cookie）——让错误在 import 处就暴露。

packages/ui — 原子组件与设计令牌

shadcn CLI 管理但基于 Base UI（style: base-nova，不是 Radix）。57 个 ui 原语 + 12 个 common 组件 + Markdown 渲染管线（react-markdown + Shiki + KaTeX）。styles/tokens.css 用 Tailwind 4 的 @theme inline 把工具类映射到 CSS 变量，全部颜色为 oklch()，半径由单一 --radius 派生；web 与 desktop 导入完全相同的令牌文件。

packages/views — 共享业务视图层

完整的功能屏幕：issues（52 个组件）、inbox、agents、chat、settings（14 个标签页组件）、layout（应用壳：DashboardLayout/AppSidebar/DashboardGuard）等。两个关键机制：

  • NavigationAdapter 端口（navigation/types.ts）：必选成员是 Next.js 与 react-router 能力的交集；两个可选成员精确编码平台差异——openInNewTab?（仅桌面标签页）与 prefetch?（仅 Web RSC）。NavigationProvider 把 push/replace 包进 useTransition，给出跨平台一致的 pending 信号；AppLink 渲染真实 <a href>（中键/复制链接/无障碍可用）再 preventDefault 走适配器，修饰键点击委托给 openInNewTab。
  • i18n：4 语言 × 25 命名空间 = 100 个 JSON；parity.test.ts 从磁盘推导命名空间清单并断言 EN 与其他语言的 key 完全对齐（归一化 i18next 复数后缀，因为中文没有语法数）；eslint-plugin-i18next 禁止硬编码文案。

packages/tsconfig

两个配置：base.json（ESNext、bundler resolution、strict + noUncheckedIndexedAccess 等额外严格项）与 react-library.json；core/ui/views 均继承后者。

  • Dockerfile（后端，两阶段）：golang:1.26-alpine 静态编译 5 个二进制（server、multica、migrate、两个 backfill 工具）→ alpine:3.21 运行时 + 迁移文件 + entrypoint。

4.4 Worktree 并行开发（值得借鉴的设计）

所有 git worktree 共享一个 PostgreSQL 容器（端口 5432 不变），隔离发生在数据库名层面。scripts/init-worktree-env.sh 从 worktree 路径确定性地派生一切：

# slug = 目录名小写化; offset = cksum(路径) % 1000
POSTGRES_DB=multica_${slug}_${offset}
PORT=$((18080 + offset))            # 后端
FRONTEND_PORT=$((13000 + offset))   # 前端

于是主检出（multica/8080/3000）与任意多个 worktree（如 multica_my_feature_702 / 18782 / 13702）可同时运行。桌面开发再叠一层：DESKTOP_RENDERER_PORT = 5174 + offset、独立应用名后缀、独立 daemon profile（~/.multica/profiles/dev-<slug>-<hash>/）。

已知陷阱 ① 永远不要把 .env 复制进 worktree——环境文件解析优先 .env，会静默连到主库；② docker compose down -v 会删掉共享卷，抹掉所有检出的数据库；③ make stop* 从不停 Postgres（专用 make db-down）。

5.3 触发智能体的四种方式

方式行为适用场景
① 指派 Issue智能体领取并进入完整任务生命周期，更新状态、发评论正式的工作项
② 评论中 @提及智能体响应但不改变 assignee/状态快速咨询、让智能体补充信息
③ Chat 私聊完全沙箱化（看不到也改不了 Issue），provider 会话恢复保持多轮上下文头脑风暴、与智能体私下讨论
④ Autopilotcron/webhook/手动触发；每次运行建 Issue 并路由（--mode create_issue|run_only）日报、定时巡检、监控响应

通知与订阅：创建/被指派/评论/被提及会自动订阅 Issue；@all 通知全工作区；子 Issue 的状态变更会冒泡给父 Issue 订阅者；失败的智能体任务会进入人类的收件箱。智能体永远不收通知。

API 调用：所有能力同时暴露为 REST API（/api/*，Bearer PAT 认证，X-Workspace-ID 选择工作区）；CLI 全部命令支持 --output json 供脚本消费。三种令牌：浏览器会话 / CLI PAT（90 天）/ daemon 令牌。

6最佳实践案例

6.1 端口-适配器模式做多端复用

同一个 IssuesPage 组件同时运行在 Next.js App Router 与 Electron 内存路由中，靠的是把平台差异压缩到一个 8 成员的接口：

// packages/views/navigation/types.ts —— 必选成员是两个路由器能力的交集
interface NavigationAdapter {
  push(path): void; replace(path): void; back(): void;
  pathname: string; searchParams: URLSearchParams;
  getShareableUrl: (path) => string;
  openInNewTab?: (path, title?, opts?) => void;  // 仅桌面（标签页）
  prefetch?: (path) => void;                      // 仅 Web（RSC 预取）
}

两个可选成员精确编码了平台分歧点，调用方必须可选调用（prefetch?.(href)），使缺失能力自然退化为 no-op，而不是运行时错误。同样的思路复制到 StorageAdapter（3 方法）与 LocaleAdapter（3 方法）。

6.2 防御性 API 边界：宽 schema + 窄类型

// packages/core/api/schema.ts —— 永不抛出，漂移降级而非白屏
export function parseWithFallback<T>(data, schema, fallback: T, opts): T
// schema 约定:
//  - 枚举用 z.string() 而非 z.enum()  → 未知枚举值仍可解析, UI 走 default 分支
//  - 数组 .default([])               → 缺字段不塌页

覆盖是风险导向而非穷举——集中在历史上白屏过的端点（时间线、评论、列表、搜索、用户）。这套设计的动机很现实：已安装的桌面客户端会连接更新的后端，响应解析必须容忍前向漂移。

6.3 事故驱动的规则固化（移动端 CLAUDE.md）

移动端的规则文件是“事故→规则”工作方式的范本：每条硬规则都附带日期与事故复盘。例如 2026-05-09 的未读数不一致事故固化为“渲染列表前必须先 grep core 的 dedupe/coalesce 预处理”；2026-05-11 的卡死加载事故固化为“硬性 30s 超时 + 手动 AbortController（Hermes 缺 AbortSignal.timeout）+ 每个 queryFn 必须解构 signal”，并给出可机检的验证命令（grep -n "queryFn: () =>" 必须零匹配）。

6.4 确定性派生的环境隔离

Worktree 隔离方案不引入任何注册表或配置中心——一切从路径哈希确定性派生（DB 名、后端/前端/渲染器端口、daemon profile、健康端口），主检出与任意多个特性分支可并行全栈运行且互不干扰。同一思想贯穿桌面开发（pnpm dev:desktop 自我隔离）与 daemon profile 系统。

6.5 部署中的实用主义权衡

  • 迁移放进容器 entrypoint 而不是 Helm Job：用 startupProbe 给迁移 5 分钟预算 + Postgres advisory lock 保证并发安全，省掉一个需要编排的 Job 资源。
  • ExternalName 别名 Service：为了让预构建镜像开箱即用，接受“每命名空间一个 release”的限制，并提供 frontend.compatibility.backendAlias=false 逃生口——权衡被明确文档化而非隐藏。
  • selfhost 端口只绑 127.0.0.1：默认安全，把暴露决策交给显式的反向代理配置。
  • Secret 带外创建 + checksum 注解滚动：机密不进 git，同时解决 envFrom 不感知 Secret 变更的滚动更新盲区。

6.6 i18n 的三重防线

① 结构防线：core 的 i18n 按执行环境拆三个入口，让 RSC 误导入在 import 时即失败；② 测试防线：parity.test.ts 从磁盘推导命名空间并断言 4 语言 key 完全对齐；③ lint 防线：eslint-plugin-i18next 禁止硬编码字符串。配合 docs 站的 conventions.mdx 作为词汇表唯一权威。

6.7 后端安全与实时性设计

  • 令牌前缀分派 + 最小权限：mat_（任务）/ mul_（PAT）/ mdt_（daemon）/ mcn_（云节点）/ JWT 五类凭证在一个中间件里按前缀分派；任务令牌被硬性绑定到单一工作区，且计费等人类专属端点用 RequireHumanActor 拒绝它——智能体拿到的凭证天然无法越权。中间件先剥掉客户端自带的 X-Actor-Source 再重新盖章，身份头不可伪造；非成员访问返回 404 而非 403，不泄漏资源存在性。
  • WS 唤醒只是提示，正确性在 HTTP：daemon 的任务唤醒走 WebSocket（低延迟），但领取始终走 HTTP claim + 3 秒轮询兜底——WS 断连只影响延迟、不影响正确性。这种“快路径提示 + 慢路径保证”的分层让实时系统的失败模式变得无害。
  • 作用域房间而非全工作区广播：WS 按 workspace/user/task/chat 作用域建房间，细粒度作用域需显式订阅并经授权器校验；个人事件永不进工作区广播。多节点扇出用 Redis Streams 分片中继，客户端以 ULID 去重容忍启动重放。
  • 输出脱敏在边界：智能体输出在写库或 WS 广播之前统一经过 pkg/redact 的密钥检测与掩码——脱敏是数据入口的义务，不是每个展示方的自觉。
